## U-20260923-06 · 2026-09-23 · A save that cannot be encoded no longer empties the file · #fix #files

- **What**: `write_file_with_encoding` opened the file with `"w"`, which empties it, and only then encoded the text. A save that could not be encoded left an **empty file** where the last good one had been. Examples: a Big5 or cp950 tab holding a character the encoding lacks, such as "€", or an encoding name Python does not know. Reproduced: `size after: 0`. It hits every save path that uses the function: Save, Save As, re-save in another encoding, auto-save, and PyBreeze's save before Run with... (found while fixing that there).
  - `write_file` (UTF-8, used by docked editors on close) had the same order, and did not catch `UnicodeEncodeError` at all: a lone surrogate in the buffer emptied the file and raised past the `JEditorSaveFileException` contract.
- **Fix**: both functions encode first and raise `JEditorSaveFileException` from an encoding failure before anything is opened. The encoded bytes are then written by a shared `_write_bytes()` under the module lock. `write_file` keeps writing the platform's line endings, as its text-mode write did.
- **Tests**: `test_text_codec.py::TestASaveThatCannotBeEncoded`:
  - a character Big5 lacks leaves the file intact;
  - so does an unknown encoding;
  - so does a lone surrogate through `write_file`, which now reports it as `JEditorSaveFileException`;
  - `write_file` still writes `os.linesep`.
- **Result / numbers**: `pytest` 1931 passed. `ruff check` clean.
- **Files**:
  - `je_editor/utils/file/save/save_file.py` (112 lines)
  - `test/test_text_codec.py`
